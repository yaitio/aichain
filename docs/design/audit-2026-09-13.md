# Audit — aichain against its own five goals

Date: 2026-09-13. Version audited: **2.17.1**. Method: measured against the
tree, CI, PyPI and GitHub, not recalled. Every number below was produced by a
command run today; where a comparison with another library rests on knowledge
rather than measurement it says so.

The five goals, as the owner stated them:

1. **Start locally, finish in stable production infrastructure.**
2. **Small and independent, so an agent can write skills, chains and agents
   quickly, simply and reliably.**
3. **No dependence on one provider; switch with one line.**
4. **Write universal code; the library adapts to each provider's quirks.**
5. **Stable for everyone, powerful for enterprise, simple and flexible for a
   developer.**

---

## Verdict, one line per goal

| # | Goal | Verdict | Evidence |
|---|---|---|---|
| 3 | Switch provider with one line | **Met, and measured** | 11 cloud providers + a private server, 90 models, one `Model(name)`; 174 (option × model) cells snapshot-tested; 9 text providers compared on 8 conversation shapes; system prompt, JSON mode and vector scores mean one thing everywhere |
| 4 | Universal code, library adapts | **Met — and it is the library's actual differentiator** | Every adaptation is reported (`last_adaptations`, 5 fates); 0 silent cells of 174; `on_unsupported` lets the caller pick strictness; `extra` valve for provider-only fields |
| 2 | Small, agent-writable | **Half met** | 1 runtime dependency (`urllib3`), 1.2 MB of source, 42 top-level names — small is true. Agent-writable is **unproven**: no `llms.txt`, no `SKILL.md`, no authoring aid; until 2.6.1 the docs taught 34 parameters that did not exist, which would have poisoned any agent writing from them |
| 5 | Stable / powerful / simple | **Simple: yes. Powerful: partly. Stable: no** | Hello world is 8 lines and 1 install. Enterprise has permissions, budgets, per-tenant keys, events — no PII, no OTel, no typing. **Eleven consecutive releases (2.7.0–2.17.0) could not be imported on Python 3.10/3.11**; 24 releases in 6 days; breaking changes shipped as minors |
| 1 | Start local, finish in production | **Not met** | The library half exists (Chain resume, stores, per-request secrets, budgets, events). The "finish in production" half is `products/` — **an empty directory**. No Lambda handler, no deployer, no template, no product |

## Where aichain genuinely beats the popular libraries

Compared against LangChain, LlamaIndex, LiteLLM, PydanticAI, the OpenAI
Agents SDK, Mastra and the Vercel AI SDK, from their documentation as of
mid-2026. These are the places a user would pick aichain *for*.

1. **It tells you what it did to your request.** No other library has an
   adaptation channel. LangChain, LiteLLM and the rest silently drop `top_k`
   on OpenAI, silently swap models for reasoning tiers, silently ignore
   image options a provider does not read. aichain records each of these as
   `translated / adapted / declined / swapped / refused`, once per
   (model, option), on the result object — and generates its reference page
   from the same run, so the docs cannot say "provider-dependent". This is
   the one capability that makes cross-provider *comparison* valid, and it
   is what the library is for.

2. **One runtime dependency.** `urllib3`. LangChain pulls in dozens;
   PydanticAI requires pydantic; LiteLLM is a large package with a proxy
   server attached. For a Lambda cold start, a corporate allow-list, or an
   agent writing code without a package manager, this is decisive.

3. **Evaluation is built into the library, with the statistics right.**
   `eval/` runs arms × cases × trials to a durable ledger and reports mean,
   `Pass^k`, `flips`, pooled ratios, paired tests, validity guards, oracle
   and noise controls — and now a debiased pairwise judge and fail-closed
   reviewer accounting. Most frameworks offer an LLM-judge scorer and a
   mean. `Pass^k` and reliability-as-a-metric are rare anywhere.

4. **Image generation across six providers behind one `Skill`**, with
   `size`/`aspect_ratio` converted per provider and the conversion reported.
   LiteLLM covers image generation but not option normalisation; LangChain
   barely covers it.

5. **Governance that fails closed.** `PermissionPolicy` with risk classes,
   `approve=` that refuses when nobody is there to ask, the approval
   conversation on the event stream, a money ceiling shared across a chain,
   a pool and the agents inside them. The OpenAI Agents SDK has guardrails
   and LangGraph has interrupts; neither has a budget in dollars that a
   fan-out cannot overspend.

6. **The event channel can rebuild a turn, not describe it.** `tool_call.*`
   carries the id, the arguments and the raw result; `run_id` is on every
   event including a nested Skill's; text streams as `text.*` on the same
   ordered channel. This is what a UI needs and what most frameworks push
   into a paid tracing platform.

7. **The agent's journal knows the difference between a fact and a claim.**
   `CHECK` vs `MODEL_CLAIM`, an `acceptance` on every result saying which it
   rests on, and a fingerprint that a caller can re-check. No other agent
   framework distinguishes "the tool returned X" from "the worker says it
   did X".

8. **Synchronous on purpose.** No event loop, no daemon, one connection per
   call. This is a *disadvantage* for a web service (see below) and a real
   advantage for Lambda and for an agent generating code that has to work
   the first time.

## Where aichain loses, honestly

1. **No async.** One `async def` in 26 000 lines. LangChain, PydanticAI,
   the OpenAI Agents SDK, Mastra and the Vercel AI SDK are async-first. Any
   web service, any concurrent request handling, any FastAPI integration
   pays for this with threads. `Pool` is a thread pool. This is the single
   largest gap for the "developer" audience in goal 5.

2. **No typed structured output.** No `pydantic`, no `py.typed`, no
   `result_type=Model`. PydanticAI's whole pitch is a validated Pydantic
   object back from the model; the OpenAI SDK and LangChain both do it.
   aichain has `json_schema` dicts and `check_structure`. Two DX riders were
   promised for 2.1.0 and never shipped — the plan admits it.

3. **Adoption is near zero, and the library did not notice its own worst
   defect.** 11 stars, 4 forks, 0 issues. Eleven unimportable releases went
   to PyPI over 14 hours without one external signal. The only observer that
   fired was the repository's own CI, and it was not being read. Whatever
   the funnel thesis says, the measured audience today is the maintainers.

4. **Ecosystem breadth.** 12 providers, 32 tools, 3 vector stores, 1 MCP
   client. LlamaIndex lists hundreds of loaders; LangChain hundreds of
   integrations; LiteLLM 100+ providers. This is a deliberate trade
   (lightness) and it is still a loss for anyone who needs the long tail.

5. **No observability platform.** Hooks and a `LoggingTracer`. No
   OpenTelemetry exporter, no Langfuse/LangSmith-style UI, no trace
   persistence. The events are richer than most; there is nowhere to send
   them.

6. **The agent is one loop.** No graph, no state machine, no explicit
   handoffs primitive. LangGraph's whole product is the graph; the OpenAI
   Agents SDK has typed handoffs. aichain has `team=` and `delegate`, which
   is enough for fan-out and not for a designed multi-agent topology.

7. **Release stability.** 24 releases in six days. Breaking behaviour shipped
   as minors: `approve` began refusing (2.6.0), mid-conversation system
   prompts began hoisting (2.9.2), `step.*` renamed (2.7.0, with a
   compatibility shim). No Windows CI; no 3.13/3.14 in the matrix although
   development happens on 3.14. Semver is followed loosely.

8. **No product.** Goal 1's second half. `products/` was created on 17 May
   and has never held a file. There is no Lambda handler, no template, no
   `deploy` command, no hosted anything. "Finish in production" currently
   means "the library will not stop you".

## The library

**Size and shape.** 25 874 lines of Python across `models/`, `clients/`,
`skills/`, `chain/`, `pool/`, `agent/`, `tools/`, `state/`, `eval/`. Largest
modules: `chain/_chain.py` (1 147), `agent/_agent.py` (1 141),
`clients/_families/_openai_compat.py` (1 077), `models/_base.py` (925). None
is unreasonably large; none has been split when it grew.

**Good**

- Provider is data (`providers/*.toml`), format is code by API family — five
  family clients serve twelve providers. Adding a provider is a TOML file when
  it speaks an existing wire format.
- Every option has a declared home (`_options.py`), a per-provider
  declaration, a value scale, and a fate. Defaults carry an author.
- `Skill` is the one place that talks to a model; `Agent` builds Skills,
  `Chain` and `Pool` run them. Money, retries, streaming and the notice
  channel all live in one place because of this.
- The agent has one loop, walked by `stream()` and exhausted by `run()`, and
  a test asserts the two agree on every script.
- Streaming reassembles tool calls from fragments on all three wire families,
  keyed on the provider's index — the trap every other implementation falls
  into is tested.
- Errors are one vocabulary (`raise / stop / skip / collect`) on Chain and
  Pool, and a failure record carries the type and the traceback.

**Bad**

- No async (see above).
- No typing surface: no `py.typed`, no mypy in CI, annotations are strings.
- `state/` suspend/resume exists for Chain only; the agent deliberately has
  none, which is defensible, but the cross-process story is therefore
  Chain-only and thinly used.
- `AgentMemory` is exported and unused by the loop — a vestige, kept "for
  eviction" that does not exist.
- `_openai_compat.py` still special-cases providers with `if p == "..."`
  branches for image paths; the plan's "put it in the data" is only done for
  options, not for endpoints.
- Tool wire names mix `convertToMD` with `vector_query` in one tool list.
- 1.2 MB of source in a 6.3 MB install (the rest is `__pycache__` and data —
  fine, but `pip install` pulls test fixtures? Unchecked.)

### Two checks that pass, and why they are not enough

Every fenced **code** example binds to the real signatures (held at zero by
`test_docs_promise_what_exists.py` and `test_lightness_invariant.py`). That
was the 2.6.1 sweep, and it is what makes the pages *runnable*. It says
nothing about **prose** — "three phases per step", "stops if max attempts
exceeded", "Text→Image: OpenAI, Google, xAI" — and nothing about **numbers**
copied by hand from a registry that has since grown. Those are where the
staleness lives now.

### Pattern

The same as everywhere else in this audit: a source of truth exists (the
registry, the option schemas, the TOML env keys, the tool classes) and a page
was written **from** it once and never **generated** from it. `parameters.md`
is the one page that cannot go stale, because it is produced by the run that
tests the code. Every table above — providers by modality, models by provider,
env vars by provider, options per tool, tools with a page — could be produced
the same way, and then this section of the audit could not be written again.

## The tests

1 448 test functions; 1 375 run in CI (73 `Live` deselected). Runtime 8–10 s
on any of 3.10/3.11/3.12/3.14.

**Good**

- The parameter matrix: 174 cells, snapshot-equality, a ratchet on silent
  cells that only goes down, and a check that the ceiling is not slack.
- Cross-provider comparison tests — one input, nine providers, compared on
  *meaning* rather than wire — which found two real defects on their first
  runs.
- Every new test this week was run against the reverted code to prove it
  bites. Several (the MRO hole, the seven-byte SSE wire, the double key
  read) exist because the first draft of the test was wrong and the
  correction is recorded in it.
- Lifecycle smokes, the lightness invariant, the docs-bind check, the
  changelog check — the plan's "Tests" section is fully closed.

**Bad**

- **Coverage is unmeasured.** `pytest-cov` is not installed; nobody knows
  which lines run. 1 448 tests is a count, not a coverage.
- **73 live tests never run in CI**, so real provider behaviour is verified
  only when someone runs them by hand with keys. Every "established by
  effect" claim in the plan rests on runs nobody can reproduce from CI.
- **CI was red for fourteen hours and eleven releases and no one looked.**
  The tests were right; the process that reads them did not exist. A
  branch-protection rule or a release workflow gated on `Tests` would have
  stopped the first broken release.
- The CI matrix is 3.10–3.12; development is on 3.14; 3.13 is nowhere.
- Test distribution is uneven: `models` 347, `clients` 300, `skills` 140 —
  `pool` 11, `chain` 28. The two primitives that compose everything have the
  fewest tests.

  invisible to the corpus.

## Prioritised list

Priority is by **distance from a stated goal**, then by cost. P0 items are
places where a goal is currently false and the fix is known.

### P0 — a goal is false today

1. **Gate releases on CI.** Branch protection or a release workflow that
   requires `Tests` green on 3.10 before `publish.yml` runs. Cost: an hour.
   Would have prevented eleven broken releases. *(goal 5: stable)*
2. **Fix the three dead examples** and put `examples/` under the same bind
   test as `docs/`. `18_agent_external_trigger.py` must be rewritten as a
   Chain, because that is the only primitive that suspends. Cost: half a
   day. *(goals 1, 2)*
3. **Decide whether the product is being built, and write that decision
   down.** `products/` is empty; goal 1 is unmet until something exists
   there or the goal is restated. This is not engineering work. *(goal 1)*
4. **Measure coverage** — `pytest-cov` in CI, a number in the README badge
   that links to a register of deliberately uncovered lines with reasons
   (the elasticgraph pattern the plan already cites). *(goal 5)*
5. **An agent-facing authoring aid** — `llms.txt` at the root and a
   `SKILL.md` that teaches an agent to write a Skill, a Chain and an Agent
   from the real signatures. Goal 2 is "an agent can write it" and nothing
   has ever tested whether one can. Then test it: give a model the skill and
   twenty tasks with auto-checks. *(goal 2)*

### P1 — a goal is weak

6. **Async.** `Skill.arun()` / `Agent.arun()` on `asyncio`, with the
   synchronous path unchanged. The largest single gap against every peer for
   the developer audience; the threads in `Pool` become an implementation
   detail rather than the only option. *(goal 5: developer)*
7. **Typed structured output** — `output=SomePydanticModel` when pydantic is
   installed, `json_schema` when it is not. Ship `py.typed`. *(goal 5)*
8. **Fill the six cookbook skeletons or delete them.** Link the four that
   map onto `rnd/` ideas; withdraw the two that do not. Apply the promotion
   rule to `council` and `idntty-games` — a test each or demote them.
   *(goal 2)*
9. **Correct `docs/index.md` and the README numbers**, and generate the
   provider/modality table from the registry so it cannot go stale again —
   the same move as `parameters.md`. *(goal 3)*
10. **Live tests on a schedule.** A nightly workflow with provider keys in
    secrets, running the 73 `Live` tests and posting the result, so
    "established by effect" is reproducible. *(goal 4)*
11. **Add 3.13 and 3.14 to the CI matrix.** Development happens on 3.14;
    CI should cover it. *(goal 5)*

### P2 — a real loss against peers, not against a stated goal

12. **An OpenTelemetry exporter** as a `Hook`. The events already carry what
    a span needs; this is a hundred lines and it puts aichain traces into
    every platform an enterprise already has. *(goal 5: enterprise)*
13. **PII masking** — the Presidio track deferred from 2.4.0. The one
    enterprise guardrail every RFP asks about. *(goal 5: enterprise)*
14. **Tests for `Pool` and `Chain`** in proportion to their role — they
    compose everything and have 39 tests between them.
15. **Endpoint routing into the data.** `_openai_compat.py` still branches on
    provider name for image paths; the plan's "put it in the data" is done
    for options and not for endpoints.

### P3 — worth doing, not urgent

16. Unify tool wire names (`convertToMD` vs `vector_query`) — a breaking
    change that needs a deprecation window.
17. Remove `AgentMemory` from the public surface or wire the eviction it was
    kept for.
18. Split `_chain.py` and `_agent.py` when next touched; both are over a
    thousand lines.
19. A Windows CI leg.

## What this audit changes about the plan

The plan is organised by mechanism and has spent the last week closing
mechanisms. Against the five goals, the mechanisms are largely done: goals 3
and 4 are met and measured, goal 5's "simple" is met, goal 2's "small" is
met. **What is not done is not a mechanism.** It is a product that does not
exist, examples nobody ran, a CI nobody read, an audience nobody measured,
and an agent nobody handed the library to. The next work is on those, and
none of it is a new module.
